# FR_OS 2.0.0-beta.1: adversarial security review (Claude Opus)

Commit reviewed: 812f985 (read-only checkout). Reviewer: Claude Opus, one of the two J2 reviewers.
Method: I read the code by hand, starting with the highest privilege and the largest attack surface. I ran `go vet` on `release/...`, `helper`, `apply` and `webui`; it found nothing. I did not run the test suites or any root, eBPF or boot tests.

Summary: **0 critical, 0 high, 2 medium, 3 low.**

I found no way to install an update without a valid signature. I also found no path traversal or symlink problem in the updater's extraction, and no way past authentication or CSRF in the webUI. The findings below are about where trust boundaries are weaker than the docs say.

---

## 1. Medium: the `publish` job signs the tarball that the keyless `image` job hands it, without checking it is the one `sign-stage` signed

**Where:** `.github/workflows/build-installer.yml:228-255` (`image` job: `cp "release/$tarball" "$tarball"; sha256sum "$name" "$tarball" > SHA256SUMS`), and `:301-336` (`publish` downloads only the `fr-os-installer` artifact, then runs `scripts/sign-sums.sh dist/SHA256SUMS`). Also `scripts/sign-sums.sh:50` and `release/verify/main.go`, which only check that the files match the list they are given.

**Scenario:** The workflow keeps the key away from the `image` job on purpose (lines 11-17, 189-190: "with no access to the signing key"). That job does a lot of untrusted work:
- it runs `sudo apt-get install` and live-build/debootstrap as root;
- it boots the freshly built image in QEMU.

Whatever that job uploads as `fr-os-installer` (ISO, tarball and `SHA256SUMS`) is signed as-is by `publish`, which has the release key. `release/verify` only confirms the files are consistent with that unsigned list. So if the `image` job is compromised (a poisoned package or build tool, or a guest escape during the boot test), it can swap `fr_os-<v>-amd64.tar.gz` for a malicious tarball and list its hash. `publish` then signs it with `FROS_RELEASE_SIGNING_KEY`. Every router accepts it in `apply.Updater` (and installs it unattended with `update.auto_install_security`), because routers check only the signature over `SHA256SUMS` plus the listed checksum. The key-isolation design is defeated without ever reading the key.

**Fix:** In `publish`, also download `release-signed`, the artifact `sign-stage` produced from the gated `stage` job. Refuse to sign unless `dist/fr_os-<v>-amd64.tar.gz` is byte-identical to that tarball, or its sha256 matches `release-signed/SHA256SUMS` verified with `release/verify`. For the ISO, consider a reproducible-build check or a second independent build. At minimum, record in RELEASING.md that the ISO's integrity rests on the `image` job.

## 2. Medium: forged packets get an innocent LAN host quarantined (TLS-FP, AI-IDS)

**Where:**
- `crates/fros-xdp-ebpf/src/main.rs:680-760` (`follow_flow` / `filter_tcp`): any TCP segment to port 443 whose payload starts a ClientHello is inspected, reported (`events`) and copied to `hello_pkts`. No handshake or conntrack state is needed. XDP runs before `rp_filter` and netfilter.
- `crates/fros-tlsfp/src/daemon.rs:190-245`: with `quarantine_on_match`, the packet's `saddr` is quarantined on the first match.
- `crates/fros-aiids/src/daemon.rs:430-460` and `engine.rs:30-33`: SNI drop events and the DNS query log feed the score. `ABS_SNI_BLOCK_COUNT_FLOOR = 3` and `ABS_DNS_THREAT_FLOOR = 3`. The DNS evidence comes from UDP queries, whose source address is unauthenticated.
- `helper/actions.go:181-305` (`checkTarget` / `quarantine`): refuses only the router's own and non-host addresses. It then looks up the victim IP's MAC in the neighbour table and quarantines that MAC as well.

**Scenario:** An attacker sits on a segment that the XDP filter watches, or that the resolver serves (for example a guest or IoT zone).
- They send a single TCP segment to any address on port 443, with a forged source IP (the victim's) and a ClientHello whose JA3/JA4 is on the blocklist. Or they send 3 such segments with a blocked SNI. Or they send 3 forged-source UDP DNS queries for a name in a malware/phishing category.
- The sensor daemons then ask the apply-helper to quarantine the victim's IP, and the helper adds the victim's real MAC.
- The victim can be any other host, including the admin's workstation or a server. It is cut off for up to 7 days (`maxQuarantineSeconds`), and the attack can be repeated.

The attacker never needs to be in the victim's zone, because XDP sees the forged source before reverse-path filtering. I checked this code path. I did not test it on a live router.

**Fix:** Only quarantine on evidence the source can't forge:
- for TLS, require the flow to be established (a conntrack lookup, or have XDP report a hello only after it has seen the SYN/ACK of that flow);
- for DNS, count only TCP queries, or queries whose IP-to-MAC binding matches;
- at minimum, have XDP include the Ethernet source MAC in events and hello copies, and have the helper refuse a quarantine when that MAC differs from the neighbour-table MAC of the IP.

Also consider a per-requester rate limit on `quarantine_ip`.

## 3. Low: `writePrivate` chowns the temp file by path, so a webUI-account process can redirect a root chown

**Where:** `webui/accounts.go:472-500` (`writePrivate`: `OpenFile(tmp, O_EXCL)` → `Close` → `os.Chown(tmp, …)` → `Rename`). It is run as root by `AdminStore.write` (`webui/accounts.go:467`, `chown = os.Geteuid() == 0`), through `firewall-cli set-admin-password` / `mfa-reset` (`helper/firstboot.go:222`, `webui/console.go`). The directory `/etc/fr_os/webui` belongs to `fr_os-webui` (0700, `apply/accounts.go:155`).

**Scenario:** The webUI has been compromised (code running as `fr_os-webui`). It watches its state directory with inotify. When the admin runs the console recovery commands as root, it renames a symlink over `auth.tmp` between root's `Close` and `os.Chown`. `os.Chown` follows the link, so any file the attacker chooses (for example `/etc/shadow`) becomes owned by `fr_os-webui`.

The webUI's `ProtectSystem=strict` sandbox limits what it can do with that file: it can't write it there. It can still read it (for `/etc/shadow`, the password hashes), and ownership changes break programs that check ownership (sudo, sshd StrictModes). The timing is tight but can be won. These are exactly the commands an admin runs after suspecting a compromise.

**Fix:** Call `f.Chown(uid, gid)` on the open descriptor before `Close`. Alternatively, open the directory and use `fchownat(dirfd, "auth.tmp", …, AT_SYMLINK_NOFOLLOW)`. A better option still is to drop to `fr_os-webui` (setresuid in a child) before writing in its directory.

## 4. Low: the webUI reads up to 1 MiB of every request body before authentication, and has no read timeout

**Where:** `webui/server.go:271-275` (`io.ReadAll(io.LimitReader(r.Body, maxBody+1))`, done before routing), `webui/fastapi.go:26` (`maxBody = 1<<20`), and `cmd/fr-webui/main.go:111-118` (only `ReadHeaderTimeout` and `IdleTimeout`; no `ReadTimeout`, no connection cap).

**Scenario:** Any host that can reach the management port, with no login, opens thousands of connections. Each sends headers with `Content-Length: 1048576` and then trickles the body. Every connection holds a goroutine and up to 1 MiB of buffer with no time limit. The webUI then runs out of memory or file descriptors, and the management plane is down for as long as the attack lasts (systemd restarts it, and the attack starts again).

**Fix:**
- Set `ReadTimeout` (or a per-request deadline through `http.ResponseController.SetReadDeadline` for routes other than SSE).
- Read the body only after the route and auth are known, or cap pre-auth bodies (login, ZTNA, MFA) at a few KiB.
- Cap concurrent connections per source (for example `netutil.LimitListener` plus a per-IP limit).

## 5. Low: a compromised parser daemon can starve the apply-helper of connection slots

**Where:** `helper/server.go:210-233` (`Serve` blocks on `slots <- struct{}{}` with `MaxConns: 32`), `helper/server.go:241-244` (30 s read deadline), and `systemd/fr-apply-helper.socket` (0660 root:fr_os-feeds).

**Scenario:** A parser daemon (`fr_os-sensor`, in `fr_os-feeds`) is compromised through a bug that untrusted traffic can reach. It keeps 32 connections open that send nothing, reopening each one every 30 s. The accept loop stops, so the webUI's requests all stall:
- `apply_confirm`, so an apply waiting for confirmation is reverted;
- `ban_ip` for brute-force sign-ins;
- `authorize_ztna`.

The peer policy is meant to make a sensor bug "not one JSON line from root"; this keeps that, but turns it into a lever against the management plane. The same pattern, with 8 slots, is in `helper/update.go:72-94` (webUI-only socket, so lower risk).

**Fix:** Count slots per peer uid, with sensors capped to a few connections. Use a short first-byte deadline (1-2 s). Never block the accept loop: close a connection over the cap right away.

## Checked and found sound (no finding)

- **Release verification** (`release/release.go`, `apply/update.go`):
  - Ed25519 over `SHA256SUMS` with compiled-in keys only. A private key, an empty list or empty data are refused.
  - The tarball name carries the version, and `checkReleaseLayout` checks the top directory and `VERSION`, so a signed list can't be replayed for another version.
  - Only newer versions install (`Apply` compares before fetching). Rollback is one level deep, to a validated version taken from root's state file.
  - The cache is verified again on every use. Work happens in a 0700 `MkdirTemp` inside the root-only `/opt/fr_os/releases`, so there is no TOCTOU between verify and extract.
  - Extraction takes regular files and directories only; links are skipped; there is a containment check and size and entry limits; no setuid bits.
  - The symlink switch is a single atomic rename.
- **Test key** (`build-installer.yml:110-116`): generated and embedded only when `release_tag == ''`. Release jobs run the tag's `sign-sums.sh`, which refuses a key whose public half isn't in `release/keys/`; only `fros-release-2.pem` is committed. The tag, `VERSION` and `GITHUB_SHA` checks and the review gate run before the build.
- **IPC** (`ipc/`, `helper/protocol.go`): bounded lines, UTF-8, duplicate keys refused, object only. `SO_PEERCRED` policy is looked up per connection. Sensors get exactly 5 commands. The update-helper re-checks for the Full role.
- **webUI auth:**
  - Server-side session store, with the session version bound to the account. The cookie is HttpOnly, SameSite=Lax and Secure on https.
  - The CSRF token is derived per session and checked with a constant-time compare on every non-GET; viewers are confined to an allowlist.
  - The MFA ticket is single-use. A TOTP step can't be replayed (checked under a mutex). WebAuthn checks challenge, origin, rpId and sign count.
  - The brute-force guard keys on `RemoteAddr` (no XFF). CSP and frame headers are sent. `template.HTML` appears only for the CSRF input and QR SVG, and both are escaped or generated.
  - The metrics bearer token is compared as a SHA-256 digest.
- **Validation:** the `config/` regexes are anchored with `\A…\z`. The helper's IPs, MACs and durations are validated before reaching nft. The ZTNA user is re-checked against the config.
- **Rust parsers:**
  - `fros-tlsfp/clienthello.rs`: checked reader, no indexing on untrusted lengths.
  - `fros-iot/mdns.rs`: bounded labels and jumps, a cap on records.
  - Privilege drop (`fros-xdp/privdrop.rs`): setgroups, then setgid, then setuid, with a check that root is gone.
- The DHCP-offer parser (`apply/netdetect.go`) is bounds-checked.
