# FR_OS 2.0.0-beta.1 adversarial review (J2) -- reviewer: claude-sonnet

Reviewed commit: 812f985 (read-only checkout). `go build ./release/ ./version/` works offline; I did not run the test suites.
No critical or high finding. The signature, checksum and extraction code of the updater is sound. The real weaknesses are in the release workflow, in the update-helper's version state, and in unauthenticated resource use on the webUI.

## Findings

### 1. [medium] The `publish` job signs a SHA256SUMS and tarball produced by the unprivileged `image` job, without comparing them to what `sign-stage` signed
File: `.github/workflows/build-installer.yml:245-246` (the `image` job builds `SHA256SUMS`), `:316-326` (`publish`), `scripts/sign-sums.sh:51`.
- RELEASING.md and the workflow header say the ISO is built "with no access to the key, from exactly that tarball".
- In `image`, `cp "release/$tarball" "$tarball"` and `sha256sum "$name" "$tarball" > SHA256SUMS` run in a job that does `sudo apt-get install`, runs live-build as root, runs QEMU, and uploads the `fr-os-installer` artifact.
- `publish` downloads that artifact and signs its `SHA256SUMS`. The only check is `go run ./release/verify`, which confirms the files match the list. It does not confirm the tarball is the one `sign-stage` signed.
- Attack: any code that runs in the `image` job (a compromised Debian mirror package, live-build hook, apt package, runner tooling) can replace `fr_os-<ver>-amd64.tar.gz` and rewrite `SHA256SUMS`. The key-holding job then signs it with the real release key. Every router would install the substituted tarball as root.
- The `sign-stage` signature over the genuine tarball exists in the `release-signed` artifact but is not used for this check.
- Fix: in `publish`, download `release-signed` as well. Fail unless the `fr_os-*.tar.gz` in `dist/` is byte-identical to the one in `release-signed`, for example by comparing the sha256 listed in the signed `release/SHA256SUMS` after `release/verify` on it. Better, publish the tarball and its `sign-stage` signature from `release-signed` directly, and sign only the ISO line freshly.

### 2. [medium] A long-running update-helper compares the target version with a stale, compiled-in "installed" version; the SEC-12 downgrade refusal can be bypassed
File: `apply/update.go:112` (`Installed: version.Version`), `:248-270` (`Apply`), `:51-54` (`UpdateServices` omits `fr-update-helper.service`), `helper/update.go:178` (`apply.NewUpdater`), `systemd/fr-update-helper.service`.
- `fr-update-helper` is socket-activated but stays running (`Type=simple`, no idle exit). After an install it is deliberately not restarted, so it keeps the old binary's `version.Version`.
- Example: router on 2.0.0, helper started as 2.0.0. The admin installs 2.0.2 through the helper. The helper still believes 2.0.0.
- An admin session (or any holder of an admin cookie plus the CSRF token) POSTs `/update/apply` with `version=2.0.1`. The helper sees 2.0.1 > 2.0.0, downloads the genuine, validly signed 2.0.1 and installs it. The router moves 2.0.2 -> 2.0.1, back to a version with the fixed vulnerabilities.
- Related effects: `state.Previous` is recorded as the stale 2.0.0, so a later rollback goes two versions back. "already running version" can misfire.
- Related edge case: `installRelease` (`:704-710`) has a branch for "this version is already the one in `/usr/libexec/fr_os`". It sets `old=""` and then calls `os.RemoveAll(dir)` on that same directory, which is the directory in use. The comment promises the opposite, and this is reachable through the stale-version path.
- Fix: determine the installed version at request time, from `/usr/libexec/fr_os/VERSION` or the `fr_os-releases/<v>` target of the symlink, not from the compiled-in constant. Alternatively exit or re-exec the helper after a successful install so systemd restarts it on the new binary. In `installRelease`, refuse (or skip) when `plain` equals the active version.

### 3. [medium] Unauthenticated CPU and memory exhaustion of the webUI: scrypt (32 MiB per call) runs uncounted for a locked account
File: `webui/routes.go:183-189` (`loginSubmit`), `webui/ztna.go:100-105`, `webui/guard.go:218-243`, `webui/passwords.go`/`webui/accounts.go` (scrypt N=2^15, r=8, p=3).
- When `accountLocked(username, ip)` is true, the handler calls `hashPassword` (32 MiB, a few hundred ms) "for the same timing" and returns. It does not call `rejectFailedLogin`, so the per-source jail never triggers.
- Getting an account locked needs only 10 failures within 15 minutes from sources that are not known for it. One source stays under the 5-failures-per-5-minutes ban with 4 failures every 5 minutes, so one host can lock any name. Failures are counted for nonexistent names too.
- After that, the same host can send unlimited concurrent `POST /login` (or `/ztna/login`, which is also unauthenticated) for the locked name. Each request allocates about 32 MiB and burns a core. 100 parallel requests is roughly 3 GB. No unit sets `MemoryMax`, and no concurrency limit exists, so an OOM can take down the webUI or other services on a small router.
- Fix: count a locked-account request as a failure for the per-source jail (`recordFailure`, which jails at 5). Bound concurrent password hashes with a semaphore of 2 or 3. Use a cheap fixed delay instead of a real scrypt for the locked path. Add `MemoryMax=` to `fr-webui.service`.

### 4. [medium] No body-read timeout in the webUI HTTP server: slow-body (slowloris-style) connections, before authentication
File: `cmd/fr-webui/main.go:111-118`, `webui/server.go:ServeHTTP` (`io.ReadAll(io.LimitReader(r.Body, maxBody+1))` runs before any authentication).
- The `http.Server` sets only `ReadHeaderTimeout` (10 s) and `IdleTimeout`. There is no `ReadTimeout`, no `WriteTimeout` (understandable for SSE, but it can be set per request with `http.ResponseController`) and no connection cap.
- A client can send headers, then trickle the body (up to 1 MiB) at 1 byte per few seconds, holding a goroutine and a connection per socket for as long as it likes. Many sockets exhaust file descriptors and goroutines. Reachable from any host that can reach the management address.
- Fix: set `ReadTimeout` (30-60 s) and use per-request deadlines for the SSE route. Add `MaxHeaderBytes` and a connection limit (for example `netutil.LimitListener`).

### 5. [low] The self-signed webUI certificate is a CA (`IsCA: true`, `KeyUsageCertSign`, no name constraints) with a 10-year validity, and the webUI offers it for download for trust installation
File: `cmd/fr-webui/cert.go:67-75`, route `GET /system/cert.pem`.
- If an admin imports `cert.pem` as a trusted root, which is the normal way to silence the browser warning, anyone who obtains the RSA key from `/etc/fr_os/webui/key.pem` (readable by the internet-facing webUI process, so by any webUI RCE) can mint certificates for any domain that this browser trusts, for 10 years.
- Fix: issue a non-CA leaf (`IsCA: false`, no CertSign). If a CA is wanted, add `PermittedDNSDomains` / `PermittedIPRanges` name constraints. Shorten the validity.

### 6. [low] No guard that a release build trusts only the release key; the test key mechanism and the `release` environment are protected only by a documented manual setup
File: `.github/workflows/build-installer.yml:107-117` (throwaway key written into `release/keys/boot-test.pem`, which is `go:embed`-ed), `release/release.go:46` (`//go:embed keys/*.pem`), `docs/RELEASING.md` ("Where the plan offers it, also tick Required reviewers").
- The throwaway key is only generated when `release_tag == ''` and its private half is deleted. That is sound for the current workflow.
- Nothing asserts at release time that `release/keys/` contains exactly the expected key set. A stray committed `boot-test.pem` or a second key would be trusted by every router built from that commit, and `go test ./release/` only checks that each file is an Ed25519 public key.
- The protection of the signing key rests on the GitHub `release` environment's tag rule `v*`. Any contributor with write access can create a `v*` tag pointing at a commit with a modified workflow. Required reviewers is optional ("where the plan offers it"), and no tag-protection ruleset is required.
- Fix: in the release path (`stage`, when `release_tag != ''`) fail unless `ls release/keys` equals the pinned list. Make required reviewers and a tag ruleset restricting creation of `v*` tags a hard setup requirement, and add a test that fails if `release/keys/` has a file not in an allowlist.

### 7. [low] The update's `Rollback` never compares versions and trusts `previous_version` only syntactically; combined with finding 2 it can install an arbitrary older signed release
File: `apply/update.go:296-312`.
- Rollback goes to the state file's `previous_version` with no check that the target is older than, or different from, the running version. The state file is root-owned (0644 in a root directory), so this is not exploitable on its own.
- With the stale helper version of finding 2, `previous_version` can be a version two releases back. Fix finding 2 first; optionally refuse a rollback target that is not strictly older than the real running version.

### 8. [low, unverified] TLS fingerprint quarantine can be triggered against arbitrary LAN hosts by a LAN peer that spoofs a source address
File: `crates/fros-tlsfp/src/daemon.rs:149-236`, `helper/actions.go:177-186` (`checkTarget` refuses only the router's own addresses, loopback and the like), `crates/fros-xdp-ebpf/src/main.rs` (records the first segment by payload shape, with no handshake state).
- With `tls_fingerprint.quarantine_on_match` on, one packet with a spoofed source IP and a ClientHello whose JA3/JA4 is on the blocklist can quarantine the spoofed host (for `quarantine_duration_seconds`, up to 7 days) at the firewall. This is an availability attack on another LAN host, such as the admin's PC or a server.
- I did not verify which interfaces the XDP filter is attached to in a default config, or whether anti-spoofing rules drop such frames before XDP sees them. Possible mitigations: require the flow to have been seen with a valid handshake, require `quarantine_on_match` to be explicit, and never quarantine a management-zone address by this path.

### 9. [low] `drop_privileges` falls back to the `nobody` account when `fr_os-sensor` cannot be looked up
File: `crates/fros-xdp/src/privdrop.rs:25-31`.
- If the `fr_os-sensor` lookup returns "no such user" (for example `fr-accounts` has not run yet on the first boot after an update), the daemon continues as `nobody`. The shared `nobody` account is less isolated than the dedicated one (other `nobody` services such as dnsmasq's child could signal or ptrace it, subject to the sandbox).
- Fix: fail closed unless a dev flag is given.

## Verified, no finding (summary of what I checked and found sound)
- `release/release.go`: Ed25519 verification, empty-data rejection, checksum lookup (exact name, first line wins), UTF-8 check, `VerifyRelease` order (signature before checksum). The tarball is read once into the hash and the same file is later extracted from a 0700 temp directory, so there is no TOCTOU between verify and extract.
- `apply/update.go` `safeExtract`: two-pass, path escape check, only regular files and directories (links skipped), mode forced to 0644/0755 (no setuid), size and entry caps, layout and `VERSION` check (`checkReleaseLayout`). The downgrade refusal itself (`Compare`) is correct apart from finding 2. The cache is re-verified on every use. The version regex is ASCII-digits only and is used for all paths.
- `scripts/sign-sums.sh`: refuses a release with no key, verifies the signing key's public half against `release/keys/` and runs the router's own check.
- Workflow: all actions are pinned to commit SHAs; the `release` environment jobs are guarded by `inputs.release_tag != ''`; the tag, commit, VERSION and review gate checks come first; `RELEASE_TAG` goes through `env:` not through script interpolation (the `steps.iso.outputs.name` interpolation is derived from VERSION and the commit SHA only).
- Helpers: `ipc` line limits and duplicate-key rejection, SO_PEERCRED per-uid role check (Full vs Sensor), the 0600 update socket, and the sensor command allowlist. Sensor-reachable commands (`quarantine_ip`, `iot_sync_isolation`, `dhcp_leases`, `conntrack_sample`) validate their input (strict IPv4/IPv6 parse that rejects leading zeros and scopes, MAC regex with `\z`, 7-day cap, 4096-MAC cap).
- webUI: HMAC-signed cookie plus server-side session id, per-session CSRF on every non-GET, role enforced centrally (viewer is read-only except its own password/MFA), CSRF not accepted from the query string, redirects built with `QueryEscape` and never from user input, `html/template` with no unsafe contexts (`template.HTML` only for the QR SVG and the CSRF input), CSP without `unsafe-inline` for scripts, `xdp.js` escapes SSE data, metrics token compared in constant time against a sha256 digest and failing closed, TOTP replay protection (`last_step`) and 5-tries-per-ticket plus 10-per-account MFA lockout, WebAuthn through go-webauthn with the RP id and origin derived per host.
- Config and renderers: the Go `regexp` `$` equals `\z`, so the one `$` regexp is safe. Names, interface names, hostnames and local-DNS entries reaching dnsmasq, nft, Kea and sshd are validated in `config` before rendering. WireGuard private keys are fed by stdin and stored 0600.
- Rust: `crates/fros-iot/src/mdns.rs` (bounded pointer jumps, `get`-based reads, record cap), `crates/fros-tlsfp` (checked `Reader`, bounded reassembly given the XDP follower limit of 3 extra segments and 2 KiB snaps), privilege drop before parsing in `fr-tls-fp` and `fr-xdp-sni-logger`, `forbid(unsafe_code)` in the workspace.
- systemd: all units carry sandboxing; sensors have `CapabilityBoundingSet=` empty and `AF_UNIX` only (except the IoT scan).
